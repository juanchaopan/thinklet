# 加题手册

这份手册讲怎么在好奇星球上做一本新书：书里的题目由哪些东西组成，什么时候复用、什么时候新建，以及开发者用 `/change` 和 `/issue next` 加书时，代理按什么步骤做、在哪些地方停下来和开发者确认。代理每次做加书、加题、加流程、加组件的 issue，先读完这份手册。

做书的过程中学到的东西，整体重写进这份手册，不在末尾追加；手册读起来要像一次写完的。

## 四样东西

一道讲题或练习由四样东西组成：组件是代码，流程、题目和书是内容文件。

| 东西 | 是什么 | 放在哪里 |
| --- | --- | --- |
| 组件 | 画在画面上、能被复用的一块，比如乐谱、钢琴键盘、选择、按键填空 | `apps/web/src/app/shared/lesson/` 下每个组件一个文件夹；参数的格式在 `packages/contracts` |
| 流程 | 一道讲题或练习从头到尾的一串幕和步骤：每一步让哪个组件做什么、老师说哪句话、等孩子做什么、得出什么结论 | `content/workflows/<流程编号>/workflow.yaml` |
| 题目 | 绑定一个流程，填上这道题自己的谱、台词、答案和评分标准，带自己的图片和录音 | `content/books/<书本编号>/questions/<题目编号>/` |
| 书 | 书本表里的一行（书名、适用年级、教学年级、学科），加上单元的顺序 | 书本表的一行写在迁移脚本里；单元顺序是 `content/books/<书本编号>/book.yaml` |

讲题和练习就是把组件装配进来，再按流程走。播放器负责把它们放在一起：画题目画面后面固定的暖色背景，放旁白和字幕，解锁声音，管静音开关。

### 组件

**边界。**一个组件只管它自己画的那一块。比如乐谱组件是一张谱纸：纸、纸上的谱、浮在上面的标签和气泡、右上角的播放按钮、短谱下面的名称。下面这些都不属于组件：

- 题目画面后面的背景，是播放器自己的样子；
- 几个组件怎么排（一行四张短谱，还是上下排），由流程决定；
- 老师的旁白和字幕，是另一个组件；
- 作答框里填什么，由作答组件管。

**接口。**组件只通过三样东西和外面打交道，不直接调用别的组件：

- **输入**：题目文件给的内容（比如谱、音域），以及模式（讲题或练习）、大小这类设置。
- **指令**：流程让它做的事，比如“聚光第 2 小节”“在这几个音上贴 A、B、C”“一个一个数”“播放”“清除”。
- **事件**：它告诉外面发生了什么，比如“孩子点了第 5 个音，是 F♯4”“数到了第 8 个半音，一共 8 个”。流程只靠事件往下走。

要让两个组件一起动（比如谱上的音和键盘上的键一起亮），是流程分别给两个组件发指令，组件之间互不知道。组件要用的服务（比如发声的“音源”）从外面交给它，组件不知道背后是什么乐器。

**外观。**每个组件的外观完全由它自己决定，不依赖外面：颜色、材质、光都定义在组件里面，不从页面或背景继承，放在哪里都是同一个样子。没有主题、配色之类的字段，流程、题目、播放器都不设这种字段。外观要有电影级别的质感，不是平面的黑白图：

- 有材质：比如谱放在有纸纹、有厚度和阴影的谱纸上；钢琴有木头琴身、红色琴毡、象牙色白键和带高光的黑键。
- 有光：标亮的东西发出柔光；聚光时其余部分变暗，光落在要看的地方。
- 有动作：按下、出现、标亮、贴标签都有短而柔的动画，减速停到位；系统打开“减少动态效果”时动画在 100ms 内完成。

**两种模式。**讲题里可以有操作，但不记录结果；练习里组件只管作答，不给提示（比如练习里的键盘只显示流程标好的东西，点了没有反应）。

**声音。**

- 讲题里乐谱能播放一段（光标跟着音符走），点音符、点琴键会发声，装饰音按实际弹法发声。练习里不放音乐，只有答对、答错、提交的短提示音，播放器有静音开关。
- 所有声音都由“音源”发出：组件只说弹哪个音、弹多长。只用钢琴（FluidR3_GM，CC BY 3.0，网站上署名），总谱里的小提琴、长笛也用钢琴弹；提示音也是音源弹的几个钢琴音。
- 手机只在孩子的操作里才能出声，有的手机在页面放过媒体之前不让网页音频出声，iPhone 的静音键也会把它静掉。所以由播放器在每次触摸时解锁声音，并一直循环播放一段无声片段；组件不管这些。

**操作。**

- 手指、鼠标、键盘都能用；可点的东西至少 44×44 像素，点不准也要点得中（比如乐谱按离手指最近的音符算，点在升降号上也算）。
- 点了以后的高亮和说明会自己淡掉，点组件里的空白处（谱纸、琴身）马上清掉；流程要求一直亮着的才一直亮着。
- 只用键盘时有清楚的焦点样式；用手指和鼠标点的时候不出现焦点框。

**文字。**组件画出来的术语和记号用这门课考试的原文（英皇乐理就用考卷上的英文、意大利文，比如 tone、semitone、enharmonic、double sharp）；中文只出现在旁白和字幕里。文字不压在图上：要指某几处时，用 (a)(b)(c)、A、B、C 或 1、2、3 这样的标记，名称写在图的外面。总谱的乐器名第一行写全称，后面几行写缩写（Vln.、Pno.），和考卷一样。

**屏幕大小。**手机、平板、电脑都要好用：宽屏上画大一些；窄屏上先换行，不缩小（乐谱按小节换行，键盘按八度换成两行，琴键不窄于 40 像素）；连一个单位（一个小节、一个八度）都放不下时，才整体缩小到刚好放下。一组同样的组件排在一起时，大小一样、对得齐。页面不能左右滚动。

**加一个组件要交的东西。**

1. 组件的文件夹和代码，在组件对照表里登记编号。
2. `packages/contracts` 里它参数的 schema。
3. 组件测试：每个状态跑 axe，三种屏幕各截一张图。
4. 在这份手册的“现有组件”一节里加一行。

### 流程

流程的文件格式在流程设计确定后写进这一节。现在已经定的：

- 讲题流程和练习流程分开，同一个题型的讲题和练习用不同的流程。
- 每个流程带一个教学年级的范围，只作参考；出题时尽量选范围覆盖这本书教学年级的流程，没有合适的就新建。
- 流程决定用哪些组件、怎么排、每一步给哪个组件发什么指令、等哪个事件。
- 练习流程写这类题默认的判分方式：整题对错、按小题算百分比，或者按步骤。

### 题目

题目的文件格式在流程设计确定后写进这一节。现在已经定的：

- 一道题绑定一个流程，选若干组件。
- 谱写成 ABC 记谱法；总谱里每个声部写全称和缩写（`name="Violin" snm="Vln."`）。
- 旁白台词写在题目文件里，用 `task narrate` 录成 MP3，放在题目的 `narration/` 里，和题目一起提交。
- 答案和评分标准写在题目文件里：每个作答点的答案（可以有几种都算对），每个作答点几分；和流程默认不同的判分方式也写在这里。
- 自己的图片只用 WebP 或 PNG；动画由组件做，题目里只写动哪个、怎么动。
- 原题不照搬：由真题改编，答案人工核对。

### 书

- 书本表的一行写在一个新的迁移脚本里：编号、书名、简介、适用年级的范围、教学年级、学科。新学科也在迁移脚本里加。
- `book.yaml` 写单元的顺序，每个单元一道讲题加几道练习。
- 封面放在 `content/books/<书本编号>/cover.webp` 或 `cover.png`。

## 复用还是新建

先找现有的组件和流程，能用就用；不能用时按下面的顺序考虑。

**组件**

1. **直接复用**：现有组件的输入和指令已经够用。比如考卷上一题有四张单音短谱，就是四个乐谱组件，排法交给流程；讲 I、IV、V 三个和弦，就是三架小键盘排成一行。
2. **扩展**：要的是同一样东西的新能力，而且这个能力只和它自己有关。比如乐谱要让装饰音按实际弹法发声、总谱后面几行写乐器缩写，加在乐谱里；新的能力要在讲题和练习两种模式下都想清楚。
3. **新建**：要画的是一样新东西，或者扩展会让一个组件管别人的事。比如钢琴键盘是新组件，不塞进乐谱；旁白字幕条是新组件，不塞进乐谱的播放按钮；“谱上的音和键盘一起亮”不需要新组件，由流程分别指挥两个组件。

判断时问三个问题：它画的是不是同一样东西？它要不要知道别的组件？加进去以后，接口还能不能用几句话说清楚？

不加开发者没要的字段和开关。想加一个可配置的东西（比如主题、配色）之前，先问开发者。

**流程**

1. **直接复用**：同一种教法，只是换素材。
2. **新版本**：教法一样，但要给另一个教学年级范围的孩子讲（低年级动画多，高年级讲得深），就新建一个范围不同的流程。
3. **新建**：想题的思路不同，或者作答和判分的方式不同。

## 做一本新书

开发者把材料（PDF、分类文件等）放在本机，按下面两步说。两个命令都只要说这几行，其余的代理会问。

### 第一步：`/change`

```text
/change 做一本新书
材料：<文件路径，一行一个>
要求：<一句话，比如“每个考点一道讲题，后面 3 道练习”>
```

代理这样做：

1. 读材料。有分类文件就直接用分类文件，只在核对细节时看原文。
2. 把题目按考点和作答形式分好类，列出这本书要哪些考点、每个考点几道讲题和练习。
3. 对照“现有组件”和“现有流程”，列出要复用、扩展和新建的组件和流程。
4. 问开发者书的信息：书名、适用年级、教学年级、学科。
5. 拆成 issue，写好每个 issue 的目标、范围和验收标准，给开发者确认后创建。

### 第二步：`/issue next`

```text
/issue next
材料：<和第一步一样的文件路径>
```

代理按 issue 的五个步骤做，在这些地方停下来和开发者确认：

1. **组件**：每个新组件和扩展，先做一个可以点的网页原型给开发者试（做法见下一节）。开发者在电脑和手机上确认样子、手感、声音和逻辑后，才做下一个。
2. **流程**：每个新流程，逐个解释为什么这样归纳、用哪些组件、一幕一幕怎么走，给开发者看原型，确认后再做下一个。
3. **书的信息和题目的信息**：书的信息在开始时问；每道题的素材、要点和答案也问开发者。
4. **每道题**：先给分镜：怎么教，一幕一幕说什么、做什么，哪些组件直接画在画面上、哪些要按按钮才弹出来。开发者确认后再做；做完开发者审过，才做下一道。
5. **手册**：每做完一个组件、流程或题目，把学到的东西整体重写进这份手册。

开发者在确认过程中改了主意（比如去掉一个字段、换一种做法），代理同时改掉 issue 正文、架构文档和这份手册里所有相关的说法，不留旧说法。

## 组件原型怎么做

原型是 issue 草稿分支上的网页，放在 `prototypes/<issue 编号>-<简短名称>/components/`，发布成可以点的页面给开发者试：

- 一页一个组件。页面顶上一段话说明这个组件是什么、边界在哪里；组件外面画一圈蓝色虚线，标上“××组件”，可以关掉。
- 组件放在暖色背景上，和真实的题目画面一样；组件自己的外观写在组件的样式里面，不用页面的颜色。
- 组件下面是“模拟流程”：一排按钮模拟流程发给它的指令，一个记录框列出它发出的事件。
- 再往下放几组考卷上真会出现的用法（比如一行几张短谱、一行三架小键盘），看排在一起是否一样大。
- 最后一张表写它的接口：输入、外观、指令、事件、依赖、谁决定排版、出现在哪里。
- 有声音的组件共用同一个 `sound.js`（音源）和钢琴采样文件，和页面放在一起发布；页面上有一行声音状态（是否就绪、音频引擎、无声片段是否在播放），手机上没声音时让开发者把这一行发过来。
- 手机上声音有问题时，用声音检查页逐项排查：网页音频、媒体播放、加载采样、解码弹奏，各一个按钮。

## 给开发者看原型之前

代理先自己检查一遍：

- 用本机的 HTTP 服务打开页面（和发布后一样能读到旁边的 `sound.js`、采样文件），在手机、平板、电脑三种宽度下截图看过：没有挤在一起、叠在一起、被裁掉的东西（尤其是窄屏上的长谱和总谱），同一组的组件一样大，页面不左右滚动。
- 每个能点的东西都用脚本点过一遍：点中的是对的，点空白处能清掉，高亮会自己淡掉。
- 每条模拟指令都跑过，事件对得上。
- 声音状态是“就绪”，没有控制台报错。
- 电脑上能听到声音不代表手机上能听到；请开发者在手机上试，并说明怎么看声音状态。

## 检查和验收

- `task content` 检查内容文件：格式、引用的流程和组件和资源都在、每句台词都有录音而且和文字一致、ABC 谱能解析、答案的格式对。
- `task narrate` 只录台词改过的句子。
- 开发者以家长身份预览每一道题，以孩子身份看完每一道讲题、做完每一道练习，明确说可以，这本书才算做完。

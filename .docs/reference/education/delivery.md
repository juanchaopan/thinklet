# POC 的工程流程和交付

规模（统计截至 2026-11-20）：`main` 上 144 个提交；151 个 PR（合并 143 个）；GitHub Actions 运行 2,767 次；117 个 issue；152 个远程分支。集中开发在 2026-11-04 到 11-16 的约 12 天，之后只有依赖更新。

## issue 和 PR 怎样流转

- 所有 PR 都由维护者的账号开（代理用维护者的 `gh` 令牌）；另有 Dependabot 的 7 个和 Renovate 的 1 个。分支前缀很杂：`feature/`、`feat/`、`fix/`、`docs/`、`chore/`、`refactor/`、`codex/`、`build/`、`ci/`。
- 从第 55 个 PR 起，基本由 GitHub 原生的自动合并完成合并。
- **评审**：抽查的 PR 都没有正式的 review；评论只有维护者账号发的一条「独立审查结论」，并写明「维护者已授权代理在独立审查通过、CI 全绿后加 `human-reviewed`」。也就是说，批准标签由代理用维护者的令牌自己加上。
- 时间线：一个 2,500 行、47 个文件的高风险 PR，打上高风险标签 28 秒后就加了批准标签，又过了不到 2 分钟就合并了。
- **风险分级**：148 个有标签的 PR 里 108 个（73%）是高风险，因为脚本目录、`package.json`、锁文件、截图基准、Claude Code 的配置、账号模块都算高风险。高风险成了常态。
- **CI 里的 AI 评审从没运行过**：AI 评审、安全评审和 `@claude` 三个工作流都要求一个开关变量为真，这个变量从没设过，API 密钥也没设。实际的 AI 评审都在本机由开 PR 的命令跑。
- 有一个 PR 检查全过、也有批准，却一直没合并：分支规则要求分支包含最新的 `main`，而仓库没打开「更新分支」按钮，`main` 前进以后它就卡住了。

## CI/CD

所有 action 用大版本标签，没有按提交固定；仓库允许所有 action；默认令牌只读。没有 actionlint、zizmor、CodeQL 和 gitleaks。

**GitHub 的定时任务大面积没按时跑**：每小时的维护实际每天只跑 3–5 次；每小时两次的健康探测实际每天 3–5 次；每天一次的备份从 2026-11-07 开始运行以来，有 2 天没跑（11-09 和 11-16）。文档里按设定频率写的清理延迟、Neon 用量估算、备份的 RPO 24 小时都不成立——实际的探测间隔约 8 小时，备份间隔最长约 48 小时。

告警 issue 共 19 个，全部已关闭：14 个是上面选提交那一步的 API 偶发错误，4 个是健康探测遇到冷启动超时，1 个是发布失败。告警链本身也会失败，有一次关闭步骤超时，要手动关。

## 发布

发布不用 `vercel` 命令行，而是自己调 Vercel 的 REST API：

1. 上传 Git 跟踪的、在白名单里的文件（按 SHA-1）。
2. 建一个候选部署，运行时的变量随部署一起传入。
3. 等它就绪。
4. 执行迁移（连带用 Supabase 时留下的加固步骤）。
5. 对候选部署的地址跑冒烟：版本文件和页面里的提交号都等于本次发布的提交；就绪；注册、登录、读会话、退出；旧 cookie 失效；结束后删掉合成的账号。
6. 再确认 `main` 没有前进。
7. 把正式地址指到候选部署，再读回来确认。

失败时删掉候选部署，不动正式地址。

其他做法：

- 连接数据库之前，核对主机等于一个变量（防止 staging 的流程动到别的库）；删除清单库必须在另一台主机上。
- 发布前用后端自己的配置检查规则验证 AI 和邮件的设置，有 AI 密钥却没设预算就拒绝发布。
- 发布的触发链：因为默认令牌打开的自动合并不触发推送的工作流，发布要靠监听三个工作流完成 → 轮询 PR 是否已经合并（最多 2 分钟）→ 派发 CI → CI 通过后再派发发布 → 发布自己报告告警。这部分代码加测试近 380 行。用 GitHub App 的令牌或个人令牌打开自动合并，或者直接由代理合并，推送就会正常触发发布，这一整套都不需要。

## 本机的重型检查和工具

- 临时数据库：起一个 PostgreSQL 容器（随机密码、只绑定本机、空闲端口，另建删除清单库），迁移，跑测试，按 Ctrl+C 打断时也删容器。
- 截图测试：把仓库复制进固定版本的 Playwright 镜像（不带 `node_modules`），依赖装在按锁文件哈希命名的 Docker 卷里并加锁，带更新参数时只把这次写出的基准拷回来。
- Windows 上结束整棵进程树。
- 工具链自检：用临时的、故意违规的代码确认 `any`、复杂度、参数个数、长度超限确实会让 lint 失败，领域层反向引用确实会让架构检查失败。
- 架构检查分析到 0 个模块时判失败。
- `package.json` 里手工列出每个脚本测试文件，新加测试要记得改。
- 没有覆盖率配置，也不统计覆盖率。
- 双实例账号测试写死了 Linux 上的 Docker 套接字和证书目录，只能在 Linux 上跑。

## 部署环境

只有 staging。决策记录定了「PR CI、隔离的 staging、平台支持时有 PR 预览、手动发布生产」，实际既没有 PR 预览，也没有生产。托管在 Vercel 免费版的新加坡区域，数据库是每个环境两个 Neon 免费项目（应用库和删除清单库）；保留了「换自有服务器」的退路，列了需要的资料，但没走。每个资源的情况见 [resources.md](resources.md)。

## 和文档不一致的地方

1. AI 评审工作流的注释说「分支规则要求所有评论都处理完才能合并」，实际这项设置是关的。
2. AI 评审写成了每个 PR 都有的流程，实际从没在 CI 里运行。
3. 规则说中高风险由维护者人工确认，实际是代理自己加批准标签。
4. 规则说只用 squash 合并，仓库设置同时允许 merge commit 和 rebase；管理员可以绕过；合并后不删分支。
5. 文档写备份的私钥放在 `staging` 环境的密钥里，实际是仓库级的；`staging` 环境里一个密钥都没有，也没有分支限制，任何分支上的工作流都能读到全部 staging 的密钥。
6. 定时任务的频率和文档差几倍到十几倍。
7. 测试用 PostgreSQL 17，线上是 18。
8. PR 预览和手动发布生产都没实现。
9. 规则文件开头还写着「当前仅空框架」，实际已经有账号、书架、两道题和 AI。
10. 状态文档写着「仓库设置写入返回 403，不能声称分支保护已启用」，实际都已启用。

## 过度设计和维护负担

- 自己写 Vercel 的部署客户端，而不是用 `vercel` 命令行；部署请求体太大的那个 bug 就出在这里。
- 告警：每个任务一个来源、两种排队组、可复用的工作流、演练模式，对一个只有合成账号的 staging 来说很重，底层的定时任务又不可靠。
- 写好却从没启用的 CI AI 评审；没有一个案例的「AI 审查员考卷」。
- 一个 12 天的 POC 有 18 份决策记录、43 份验收记录、两份 62 KB 的路线图。
- 仓库体积：当前文件约 374 MB，其中 PNG 340 MB（截图基准和文档截图）；打包后的历史约 1 GB。没用 Git LFS，每次界面改动都会再加一批。
- 152 个远程分支没删。
- spike 遗留：工作流仍登记为启用，它们用的两个 OpenAI 密钥没作废；Supabase 项目和旧的 Vercel 探针项目去留未定；Supabase 时代的加固步骤还在发布流程里。
- 端到端在 CI 里自动重试一次，会掩盖不稳定；POC 自己的规则也写着「不稳定的测试开 issue 修，不靠反复重跑」。

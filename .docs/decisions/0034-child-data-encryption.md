# 0034 孩子个人信息加密

## 背景

指标和 REVIEW.md 要求孩子的个人信息加密保存，#8 是第一个存孩子信息的 issue：昵称、账号和记住的设备名称。账号要在家庭内唯一，登录时要按账号查找。

## 比较过的方案

- 在应用里按字段加密。
- 只靠数据库的磁盘加密。
- 密文要不要绑定它所在的位置：附加认证数据（AAD）只有密钥编号；再加上表名、列名和这一行的主键。

## 决定

- 后端用 `node:crypto` 的 AES-256-GCM 按字段加密昵称、账号和设备名称，每次随机的初始向量，密文带密钥编号。
- 附加认证数据（AAD）里有密钥编号、表名、列名和这一行的主键，密文换到别的行或别的列就解不开。已有的密文由代码写的数据迁移全部重新加密（决策 0018），之后只认新格式。
- 账号另存一个 HMAC-SHA256 查找值（同一个家庭里同一个账号算出同一个值），数据库用它做家庭内唯一约束，登录时用它查找。
- 加密和查找的两把子密钥，以及按来源限流的键用的第三把子密钥（决策 0039），都由主密钥 `CHILD_DATA_KEY`（32 字节随机数）用 HKDF 推出。它是后端运行时的密钥，由代理随机生成，直接写进 GitHub，不显示。
- 加密和解密放在 `infrastructure`，repository 读写时调用，service 和 controller 只见明文。

## 理由

- 只靠磁盘加密的话，能连上数据库的人、数据库的导出和备份里都是明文；按字段加密后，没有密钥只看得到密文。
- Node 自带 AES-256-GCM、HMAC 和 HKDF，不加依赖；GCM 能发现密文被改过。
- 密文带密钥编号，以后换密钥时新旧密文能并存。
- 只有密钥编号的 AAD 挡不住有数据库写权限的人把两个孩子的昵称互换，或者把账号的密文搬进昵称；绑定位置后，搬动过的密文解密时就会报错。

## 代价

- 数据库里不能按昵称排序和搜索，要读出来解密后在后端排。
- `CHILD_DATA_KEY` 丢了，这些数据就再也读不出来；泄漏了要换密钥，并把全部密文重新加密。
- 每个字段多存一点数据，每次读写多一次加解密。
- 新建一行之前就要知道它的主键，主键由后端生成，不能用数据库的默认值。
- 改表名、列名或主键的迁移，要把这一列的密文重新加密。

## 何时重新考虑

- 要按孩子的信息搜索或排序的数据量变大。
- 建生产环境，可以用云服务商的密钥管理服务。

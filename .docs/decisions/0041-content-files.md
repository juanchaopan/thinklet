# 0041 内容文件：组件、流程和题目

## 背景

#20 要做第一本有内容的书（英皇乐理五级精讲）：一道讲题接几道练习，讲题一幕一幕地播放，有旁白、字幕和操作，练习要判分。以后别的学科和题型也按同一套结构加，加题由 AI 代理按手册来做。用户要求组件是代码，流程和题目本身的资源都是文件；加一个新流程只加文件，不改播放讲题和练习的代码。

## 比较过的方案

- 内容文件的格式：YAML；JSON。
- 单元和题目的目录放在哪里：仓库里的文件是唯一来源，导入时重建进数据库；目录也写成迁移脚本，进度表用外键引用题目。
- 流程和教学年级：题目直接绑定一个流程，流程的教学年级范围只作参考；题目只选题型，播放时按书的教学年级自动挑流程的版本；固定三个年级档。
- 题目自己的资源：图片 WebP、PNG 和 MP3，动画由组件代码做；再加 SVG 和 Lottie 动画文件。
- 内容的检查：新加静态检查 `task content`，放进 `check` 和 PR CI；只在导入时检查。
- 加题手册放在哪里：`content/README.md`；`.docs/design/content.md`。

## 决定

- **组件**是前端代码（`apps/web/src/app/shared/lesson/`），跨题型复用，参数的格式是 `packages/contracts` 里的 Zod schema。
- **流程**是 YAML 文件 `content/workflows/<流程编号>/workflow.yaml`：一道讲题或练习从头到尾的一串幕和步骤；练习的流程还写这类题默认的判分方式。每个流程带一个教学年级的范围，只作参考。
- **题目**是 YAML 文件 `content/books/<书本编号>/questions/<题目编号>/question.yaml`：绑定一个流程，选若干组件，写谱、旁白台词、答案和评分标准；题目自己的资源放在同一个文件夹的 `images/`（WebP、PNG）和 `narration/`（MP3）里。不收 SVG 和动画文件，动画由组件实现，文件里只写动哪个、怎么动。
- **书**的单元顺序写在 `content/books/<书本编号>/book.yaml`：每个单元一道讲题加几道练习。书本表里的那一行仍然由迁移脚本写（决策 0035）。
- 出题时选范围覆盖书的教学年级的流程，没有合适的就新建一个；对不上不算错。
- 仓库里的文件是内容的唯一来源。内容导入（`task rebuild`）校验全部内容，通过后把文件传到对象存储、重建题目表；有一项不对就什么都不改。练习结果和学习时间按题目编号存，不用外键。
- `task content` 只读 `content/`，不连数据库和存储，检查格式、引用、录音和台词一致、ABC 谱能解析、答案的格式；放进 `task check` 和 PR CI。内容导入用同一套校验。
- 加题手册是 `content/README.md`，`AGENTS.md` 引用它：目录结构、文件格式（指向 schema）、现有组件和流程的清单、加书加题加流程加组件的步骤，以及 `/change` 和 `/issue next` 加题时的模板。

## 理由

- YAML 写中文旁白、多行文字和 ABC 谱最清爽，能写注释；浏览器只读导入时转好的 JSON。
- 加题、改题只改文件，不用每道题都写一个高风险的迁移脚本；内容由仓库决定，重新导入结果一样。
- 题目直接绑定流程，出题的人清楚这道题怎么教；自动挑版本会让同一道题在不同的书里讲法不同，难以审阅。
- 不收 SVG 和动画文件，就不用清洗里面的脚本，也不多一个播放库；乐理书用组件动画就够。
- 内容错在 PR 里就能发现，不用等到发布。
- 手册放在内容旁边，在 GitHub 上打开 `content/` 就能看到；它讲的是做法，不是设计，放在 `.docs/design/` 里不合适。

## 代价

- 题目从内容里删掉，它的练习结果和学习时间还留在表里，只是不再显示。
- 流程的写法是一套小的描述语言，播放器要能解释它；流程写错要靠内容检查和组件测试发现。
- 只改内容的 PR 是中风险，每次都要人批准。
- 以后要 SVG 或自带动画的题，要再改这个决定。

## 何时重新考虑

- 内容多到仓库和导入吃力，或者要让编辑在网页上改题。
- 出现组件实现不了、只能用动画文件的教法。

# 0016 代码结构

## 背景

代码要分层、分模块，结构由架构规则检查来保证，每一层还要有对应的测试要求。

## 比较过的方案

- 后端：按业务分模块，模块内分三层；六边形架构（端口与适配器）；按技术分目录。
- 前端：core / features / shared；按技术分目录。
- 分层测试：按层定测试种类；只要求单元测试。

## 决定

- 后端每个业务是一个 NestJS 模块，模块内分 controller、service、repository 三层，只能从上往下调用。模块之间只调用对方导出的 service。数据库、对象存储、配置和日志的接入放在 `infrastructure`。
- 前端分 `core`、`features/<业务>`、`shared/ui`：features 按路由懒加载，彼此不互相引用；`shared` 不引用 `features`。
- 前后端只通过 `packages/contracts` 共用代码。
- 测试：后端 service 和共用包写单元测试；repository 和 controller 写集成测试，连真实的 PostgreSQL；前端组件写组件测试；完整的流程写端到端测试。

## 理由

- 按业务分模块，改一个功能只动一个目录；三层的职责清楚。
- 六边形架构的文件和接口很多，对现在的规模偏重。
- 数据库查询要连真实数据库才能测出错误。

## 代价

- 业务规则和框架绑在一起，以后换框架时改动大。

## 何时重新考虑

- 业务规则变得复杂，需要脱离框架单独测试。

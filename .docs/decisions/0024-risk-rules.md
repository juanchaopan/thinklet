# 0024 风险规则

## 背景

每个 PR 按改到的文件分成低、中、高三级风险。中、高风险的 PR 合并前要有人批准。

## 比较过的方案

- 用常见的起点，改成本项目的路径。
- 另外把 `packages/contracts/**` 也算作高风险。
- 低风险里去掉 `**/*.md` 和 `**/*.txt`。
- 存家长和孩子数据的后端模块：逐个列进高风险；把 `apps/api/src/modules/**` 整个算作高风险。

## 决定

用常见的起点，改成本项目的路径，写在仓库根目录的 `risk-rules.yml` 里。具体路径见 `architecture.md` 的“风险规则”一节。

- 高风险：流程和检查本身、截图基准图、登录认证、存家长和孩子数据的后端模块、迁移脚本、环境文件、部署配置、`apps/api/src/infrastructure/**`。
- 存家长和孩子数据的后端模块逐个列出：`auth` 由 `**/auth/**` 覆盖，`family` 是 `apps/api/src/modules/family/**`。以后新加这类模块的 issue，把它的路径加进来。
- 低风险：`.docs/**`、`**/*.md`、`**/*.txt`、`LICENSE`。
- 同时属于两边的，按高风险算。
- 发版 PR 一律是高风险。

## 理由

- 放宽检查、改基准图、改 CI 都必须有人看过。
- 接口约定包几乎每个功能都会改，算成高风险会让大部分 PR 都变成高风险。
- 家长和孩子的个人信息、家庭成员和权限出错代价最大；只列这些模块，不碰个人信息的业务模块（比如书库）仍是中风险。

## 代价

- 改界面的 PR 一般会更新截图基准图，所以都是高风险。
- 新加的存个人信息的模块要记得列进来，漏了就只是中风险。

## 何时重新考虑

- 加了存孩子数据的模块。
- 高风险的 PR 多到批准成为负担。

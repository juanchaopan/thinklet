# 0017 基础设施怎么建

## 背景

测试环境只有两个 Vercel 项目、一个 Neon 项目和一个存储桶。生产环境在国内云上，本来就和测试环境不同。

`vercel` 命令行自带的构建依赖锁定了一批有高危漏洞的旧包。写进仓库的依赖清单，每个 PR 的依赖漏洞检查都会失败。

## 比较过的方案

- 直接用 `vercel` 和 `neonctl` 命令行创建，命令记在架构文档里。
- 用 OpenTofu 写成基础设施即代码。

两个命令行怎么装：

- 不写进仓库的依赖清单，按固定版本临时运行：CD 在 GitHub 的临时机器上用 `npm install --global` 装 `vercel`，本机用 `npx`。
- 写进根目录的开发依赖，在依赖漏洞检查里为它们带进来的包开例外。

## 决定

- 直接用 `vercel` 和 `neonctl` 命令行创建。命令记在 `architecture.md` 的“Deployment targets”一节，执行前先用 `--help` 核对参数。
- 两个命令行都不写进仓库的依赖清单，按固定版本临时运行。`vercel` 的版本写在部署工作流的 `VERCEL_CLI_VERSION` 里，由 Renovate 更新；`neonctl` 只在建资源时用 `npx` 运行，版本写在命令里。

## 理由

- 资源很少，不用多学一个工具，也不用找地方存状态文件。
- 测试环境和生产环境本来就不同，用代码保持两边一致的好处不大。
- Neon 的官方 Terraform provider 还是测试版。
- 有漏洞的包只在部署和建资源时运行，不进产品；不进依赖清单，就不用维护一份漏洞例外清单。

## 代价

- 在网页控制台里做的改动不会被发现。
- 重建环境要照着命令手动再执行一遍，容易漏掉参数。
- 依赖漏洞检查看不到这两个命令行和它们的依赖。
- 本机和 CD 用的 `vercel` 版本要靠命令里写的版本号保持一致。

## 何时重新考虑

- 建生产环境时，资源多了，或者要频繁重建环境。
- `vercel` 命令行不再带有高危漏洞的依赖。

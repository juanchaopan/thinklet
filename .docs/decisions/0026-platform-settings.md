# 0026 平台设置

## 背景

仓库是 GitHub 免费账号上的公开仓库。公开仓库在每种套餐上都能强制执行分支规则和必过检查，也能按环境保存密钥。

## 比较过的方案

- 分支规则：严格，管理员也不能绕过；同样的规则，但管理员可以绕过。
- 远程 issue 分支：永久保留；合并后删除。
- App：只装 Renovate；Renovate 和 Vercel 都装。
- `risk`、`risk-gate` 和去掉批准标签的任务：按 `pull_request` 事件运行，代理合并前再自己核对一遍；改用 `pull_request_target`，始终运行 `main` 上的工作流文件。

## 决定

- `main` 的规则：只能通过 PR 合并，只允许 squash；必过检查要全部通过；分支必须包含最新的 `main`；评论线程要全部解决；禁止强推和删除；管理员也不能绕过。
- 人的批准靠 `risk-gate` 和 `human-reviewed` 标签，不设“必须有几人批准”。
- 这几个任务按 `pull_request` 事件运行。代理合并前不只看 `risk-gate`：自己用目标分支的脚本和 `risk-rules.yml` 算出风险等级，中风险和高风险的 PR 还要确认 `human-reviewed` 是在最后一次提交之后加上的。
- 远程 issue 分支永久保留，本地分支合并后删除。
- 只装 Renovate（Mend）的 App。

## 理由

- GitHub 不让 PR 作者批准自己的 PR，所以人的批准用标签来做。
- 合并前再核对一遍，改动小，马上就能验证；`pull_request_target` 产生的检查能不能算作 PR 的必过检查，要等 `main` 上有了工作流才能试。
- fork 来的 PR 拿到的令牌只能读，改不了标签，`risk-gate` 一定失败，外人改不掉这道关。
- 保留分支，每个 issue 每一步的提交以后都还能查。
- Vercel App 会自己触发发布，和“只由 GitHub Actions 部署”的决定冲突。

## 代价

- PR 能改掉 `risk-gate` 自己的工作流，让它在没人批准时也显示通过；只有代理合并前的核对能发现。人自己在网页上合并时，要自己看风险标签和批准标签。
- 规则本身出问题时，要先在设置里暂时把它关掉。
- 远程分支会越来越多。

## 何时重新考虑

- 仓库改成私有（那时要 Pro 或 Team 套餐才能强制执行分支规则）。
- 有其他人加入，或者有人要从网页上直接合并 PR。

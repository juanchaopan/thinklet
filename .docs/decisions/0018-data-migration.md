# 0018 数据迁移

## 背景

数据库里的数据不全是代码生成的，表结构要跟着代码的版本走。#9 加了年级、学科和书本的数据，以及完全由仓库里的文件生成的封面。#14 要把孩子个人信息的密文全部重新加密（决策 0034），这要用到 `CHILD_DATA_KEY` 和后端的加密代码，SQL 脚本做不到。

## 比较过的方案

- 数据库：Drizzle Kit；node-pg-migrate；dbmate。
- 书本数据：用迁移脚本写进数据库；仓库里的 JSON 由导入命令同步。
- 封面：后端里的封面导入命令重建。
- 其他文件：等第一个存这类文件的 issue 再定；现在就做一个小的文件迁移程序。
- 要用代码或密钥才能改的数据：`task migrate` 在 `drizzle-kit migrate` 之后再执行按版本编号的 TypeScript 数据迁移；单独的一次性重新加密命令；后端读新旧两种格式，写的时候慢慢换掉。

## 决定

- 数据库用 Drizzle Kit，按版本逐个迁移：
  - 脚本放在 `apps/api/drizzle/`，执行命令是 `drizzle-kit migrate`，执行记录在表 `__drizzle_migrations` 里。
  - 只能往前迁移；合并过的脚本不再修改，写错了就再写一个新脚本。
- 年级、学科和书本的数据也用迁移脚本写入和修改（决策 0035）。
- 要用代码或密钥才能改的数据，写成 `apps/api/src/data-migrations/` 里按版本编号的 TypeScript 文件，由入口 `apps/api/src/migrate-data.ts` 按顺序执行：它用 NestJS 的应用上下文只启动数据库和要用的 infrastructure，每个迁移在一个事务里执行，执行过的记在表 `data_migrations` 里。规则和 SQL 脚本一样：只能往前，合并过的不再修改。`task migrate` 先执行 `drizzle-kit migrate`，再执行它；CD 的这一步带上 `CHILD_DATA_KEY`。
- 封面按重建处理：由后端里的封面导入命令 `task rebuild` 从 `content/books/` 同步，在迁移之后执行。
- 执行的时机，都是先 `drizzle-kit migrate`、再代码写的数据迁移、最后导入封面：
  - 测试环境：CD 发布前执行，用 Neon 的直连地址。
  - 生产环境：在它的部署任务里执行，允许停机。
  - 开发机和测试数据库：创建时执行。
- 对象存储里的其他文件暂不迁移，等第一个存这类文件的 issue 再定。

## 理由

- Drizzle Kit 和 Drizzle ORM 是一套，表定义只有一份，脚本由它生成后还可以手改。
- 封面完全由仓库里的文件决定，重新导入就得到同样的结果。
- 图片、音频本身没有结构，多半不用迁移：要换就上传新文件，由数据库记录用哪个。
- 代码写的数据迁移和 SQL 脚本按同一套规则执行和记录，每个环境都在同一个时机跑，迁移测试也能照样写；一次性命令以后每遇到一次就要再加一个命令和一步 CD。只读新格式，迁移跑完，旧密文就全部换掉了；新旧两种都读，旧密文不知道什么时候才换完。

## 代价

- Drizzle Kit 不支持回退，出了问题只能再写一个新脚本来修；代码写的数据迁移也一样。
- 迁移数据的那一步要拿到 `CHILD_DATA_KEY`，CD 里多一个用到它的地方。
- 重新加密跑完到新后端上线之间，还在运行的旧后端读不了新密文，孩子相关的页面会出错几分钟；架构允许发布时停几分钟。

## 何时重新考虑

- 要在对象存储里存有结构的文件（比如 JSON）。
- 出现用户上传、不能由代码重建的文件。

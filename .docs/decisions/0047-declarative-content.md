# 0047 声明式的内容：流程、题目、主题和执行它们的引擎

取代决策 0041 里内容放在仓库、题目和流程文件的写法、组件自己负责全部外观这几部分；0041 里内容检查、导入校验、不收 SVG 和动画文件的决定照旧。

## 背景

做第一本书的第一道题时发现，流程和题目文件虽然是 YAML，播放器里却写着某个流程才有的概念（小题、读题、题目条、结论板的位置），组件的大小由自己的内容决定、排版没有全局的规则，组件的颜色也写死在组件里。用户要求：只有组件和执行文件的引擎是代码；流程和题目完全是声明式的，流程像一个带形参的剧本，题目只选流程、主题和组件，再传入实参；排法按屏幕大小写在流程里；颜色等外观常量放在和组件无关的主题里；内容不进代码库，放在对象存储里。

## 比较过的方案

- 内容放在哪里：仓库的 `content/`，导入时上传到对象存储；单独的内容仓库，合并后上传；对象存储就是唯一来源，从开发机检查后直接上传。
- 流程怎么写：流程里声明小题的种类、角色和固定的舞台位置；流程只声明形参、组件占位、排法、幕和幕的顺序，别的概念由各个流程用这几样自己表达。
- 排版：播放器按固定的几块（顶栏、结论板、题目条、中间、底栏）排；流程按屏幕条件把舞台划分成区域，每一幕说每个区域放什么。
- 颜色：组件自己定；主题文件给出常量，组件只用常量的名字。

## 决定

### 理念

- **代码和内容分开。** 代码库里只有引擎、组件、接口的定义和文件的格式。书、题目、流程、主题都是声明式的文件，和题目用的录音、图片一起放在对象存储里。加题、改流程、换一套颜色，只上传文件，不发版。
- **引擎执行内容。** 浏览器不能直接执行 YAML。引擎是浏览器里的 JS，读这些文件，照着摆组件、调接口、按步骤走、做动画。引擎里不出现任何一个流程、题目或组件的名字。
- **流程是带形参的剧本。** 流程声明自己要的参数、要哪些组件占位（只按接口，不写死是哪个组件），以及排法和每一幕。题目只说用哪个流程、哪个主题，再把实参传进去：数据，以及每个占位用哪个组件。
- **组件只管功能。** 组件决定自己的形状、大小、行为和接口。颜色等外观常量来自主题：换主题只换边框、前景、背景这些颜色，不改组件的大小和行为。
- **只用有限的声明式词汇。** 文件里没有表达式和脚本，只有：条件 `when`、对列表重复 `for`、取值 `$名字`、按名字引用（屏幕、排法、幕）。要逻辑的地方，逻辑做成组件的接口，或者做成引擎的通用词汇。
- **检查兜底。** 文件写错不会编译失败，所以引擎开讲前、上传前、导入时，都用同一套规则把文件和它引用的一切核对一遍。

### 对象存储里的文件

```text
books/<书名>/                     文件夹：一本书
  book.yaml                       文件：书本身
  cover.webp | cover.png          文件：封面
  items/<题目名>/                 文件夹：一道题，只属于这本书
    item.yaml                     文件：这道题
    <任意名字>/                   文件夹：这道题的录音、图片等，由 item.yaml 的参数按相对路径引用
workflows/<流程名>.yaml           文件：一个流程
themes/<主题名>.yaml              文件：一个主题
```

- 名字用小写字母、数字和连字符；文件夹名、文件名就是名字，文件里不再写编号。
- 书名就是书本表里的书本编号。题目名在这本书里唯一；题目表记下书名和题目名，练习结果和学习时间按它指向题目。流程和主题没有数据库表。
- 题目要在另一本书里用，就拷贝到那本书的文件夹里。

### `book.yaml`

格式由产品固定，书本页面读它：`title` 书名；`grades` 适用年级和教学年级；`units` 是数组，按书里的顺序，每个单元写一道讲题 `lecture` 和几道练习 `practices` 的题目名。

### `item.yaml`

```yaml
workflow: <流程名>
theme: <主题名>
components: # 流程的每个组件占位用哪个组件（流程给了默认组件的可以不写）
  <占位名>: <组件名>
params: # 流程要求的参数，名字、类型、必填与否全由流程决定
  <参数名>: <值>
```

除了这四项，题目里没有别的东西。标题、题干、要讲的数据、台词、答案，都是流程要求的参数；录音、图片的文件夹也是参数，写相对路径。显示在哪里、什么时候显示、怎么动，都由流程决定。

### `workflows/<流程名>.yaml`

按这个顺序写：

| 部分       | 写什么                                                                                                                                                                                                               |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `summary`  | 这个流程是干什么的                                                                                                                                                                                                   |
| `params`   | 形参：每个参数的名字、类型、是否必填、说明；列表写每一项的字段。类型有：文字、数字、是或否、列表、字典、文件夹、文件，以及接口定义的类型（例如某种输入格式）。练习的答案和评分标准也是形参，标成只给后端             |
| `controls` | 组件占位：每个占位要的接口，可以给一个默认组件；它的输入从哪里来（`$参数`、常量，或者引擎提供的上下文，例如 `$book` 里这本书的题目清单、`$item` 里这道题的题号）。输入有哪些、什么格式，由接口定义                   |
| `screens`  | 命名的屏幕条件：最小、最大的宽、高和宽高比，按 CSS 像素                                                                                                                                                              |
| `layouts`  | 命名的排法。一个排法是几种按屏幕条件选用的具体排法：每种用行、列和区域图把舞台划分成几个区域，并设定每个区域里的东西怎样排、怎样缩放。同一个排法的每种具体排法区域名相同，只是位置和大小不同；最后一种不写条件，兜底 |
| `scenes`   | 命名的幕：用哪个排法，每个区域放哪些占位，占位在这一幕开始时的状态，上台、下台的动作，这一幕能不能在做完前往前越过、做完后等不等，以及一步一步做什么                                                                 |
| `sequence` | 幕的顺序：幕名，或者一组“对某个列表参数的每一项”重复的幕（`for`）；可以带 `when` 和给幕的参数；每组可以有一个分段名，分段切换的控件用它                                                                              |

区域的设定：`flow`（横排、竖排）、`align`（靠哪边）、`gap`、`grow`（谁占满剩下的地方）、`fit`（组件自己的大小，或者整体缩放进区域）、`width`（先按多宽画）、`zoom`（缩放的最小、最大倍数）、`maxHeight`（高度跟着内容走时最高多少）、`overflow`（缩到最小还放不下时变成转盘，或者继续缩小）、`over`（叠在另一个区域上）、`layer`（前后）。

一步：

| 写法                                         | 做什么                                                                                                             |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `do: { control, call, with, wait, from }`    | 调一个占位的接口命令。`wait` 是否等它做完；`from` 把另一个占位在屏幕上的位置一起给它（例如让一样东西从那里飞过来） |
| `together: [步骤…]`                          | 几步同时做，例如一边说一边指                                                                                       |
| `await: { control, event, accept, onWrong }` | 等孩子操作：等占位报告事件，按 `accept` 判断；`onWrong` 是第几次不对时做的步骤                                     |
| `enter`、`exit`：占位名，`motion`            | 让一个占位上台或下台                                                                                               |
| 任何一步加 `when`                            | 条件满足才做                                                                                                       |

动作：留在台上的东西自动从原来的位置和大小滑到新的。上台默认升起淡入，下台默认原地淡出；也可以写 `fly`，下台时飞向目标并缩进去，上台时从目标长出来；`cut` 是直接出现或消失。目标是一个占位、一个区域，或者某个占位里的某一项（由它的 `positions` 接口给出位置）。动作的时长和缓动是引擎的，不写在流程里；系统要求减少动态效果时，动作直接到终点。

### `themes/<主题名>.yaml`

主题只有常量：一组颜色（边框、前景、背景等），以及其他不改变组件大小和行为的外观常量。常量的名字由代码库里的主题格式规定，所有组件（包括关闭、字幕这些每道题都有的控件）和舞台的背景只用这些名字；主题文件给出它们的值。题目选一个主题，台上的一切都按它渲染。

### 区域里的大小

- 区域的大小由排法决定，不由组件的内容决定。
- 内容放不满区域：居中，在 `zoom` 允许的倍数内放大。
- 内容超出区域：先在 `zoom` 允许的倍数内缩小。还放不下时，一个区域里有几个组件，就把这几个组件排成转盘；只有一个组件，就由组件自己把它的几项排成转盘。转盘一般只沿一个方向转，信息很密的组件才两个方向都转；焦点上的一项正常大小，两头的变小变淡；手指、滚轮、拖动都能转。

### 代码库里的东西

| 东西             | 在哪里                                                                | 写什么                                                                                                                                                    |
| ---------------- | --------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 引擎             | `apps/web/src/app/shared/lesson/engine/`                              | 注册表、检查、进程、排版、动作、转盘、主题（下表）                                                                                                        |
| 组件             | `apps/web/src/app/shared/lesson/components/<组件名>/`                 | 名字；实现哪些接口；内容放不下时沿哪个方向转；功能和形状；颜色只用主题常量的名字                                                                          |
| 接口             | 命令、事件的类型在 `shared/lesson`，输入的格式在 `packages/contracts` | 名字；输入的格式；命令和它的参数；事件；能取出和摆回的状态                                                                                                |
| 文件的格式       | `packages/contracts`                                                  | 书、题目、流程、主题文件的结构，主题常量的名字，接口输入的格式。前后端共用，所以放在这个包里。题目的 `params` 没有固定的 schema，按它的流程声明的形参检查 |
| 检查、导入、发布 | `apps/api/src/` 和 `tools/`                                           | 见下面「检查和发布」                                                                                                                                      |

组件不知道流程、题目和别的组件，也不知道舞台多大，只知道引擎给它的盒子。

引擎的各部分：

| 部分   | 做什么                                                                                                                                                                    |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 注册表 | 组件按名字登记它实现的接口；引擎只通过它找组件，只通过接口和组件说话                                                                                                      |
| 检查   | 开讲前核对；有问题不开讲，列出问题                                                                                                                                        |
| 进程   | 按 `sequence` 展开成一串幕，按 `when` 取舍、按 `for` 重复；`$` 取值；一步一步执行；每一幕开始时记下所有组件的状态，往回、跳过时直接摆回去；按幕的设定决定能不能往前、往回 |
| 排版   | 按屏幕条件选具体排法，划分区域，把占位放进区域，按区域的设定缩放、放大、排转盘，给每个组件它的盒子；屏幕变了就重排                                                        |
| 动作   | 换幕、换排法、某一步上下台时：留下的滑过去，新来的进来，离开的离开或飞向目标                                                                                              |
| 转盘   | 区域和组件共用的同一种转盘                                                                                                                                                |
| 主题   | 把题目选的主题常量交给所有组件和舞台                                                                                                                                      |

### 检查和发布

- 对象存储是内容的唯一来源，测试环境和生产环境各有自己的存储桶。不假设存储桶有版本记录：覆盖就是替换。
- 写内容在开发机上的一个工作文件夹里，结构和存储桶一样，不在代码库里。先从存储桶取下来再改。
- `task content` 检查工作文件夹，不连数据库和存储：每个文件符合格式；书引用的题目都在这本书里；题目的流程、主题存在，每个没有默认组件的占位都选了组件，组件实现了占位要的接口；参数和流程的形参对得上（必填的都填了，没有多填，类型对），引用的文件夹和文件存在，每句台词都有和文字、声音设置一致的录音；流程引用的屏幕、排法、幕、占位都存在，每种具体排法的区域图是矩形、区域名一致，每一幕放进区域的占位在每种具体排法里都有区域，动作的目标存在，指向某一项时目标组件实现了 `positions`，兜底的具体排法不写条件。
- 内容发布命令先做同样的检查，通过后把工作文件夹和存储桶对齐：上传新的和改了的文件，删掉文件夹里已经没有的；然后启动这个环境在 GitHub Actions 里的内容导入任务。先发布到测试环境，用户在测试环境看过以后再发布到生产环境。发布用的是只能写这个存储桶的凭据，用户把它存成不提交的文件，命令从文件读入，不显示。
- 内容导入（`task rebuild`）读存储桶，用同一套规则再检查一遍，然后记下封面的散列、重建题目表；CD 在迁移之后也执行它。它不再读仓库。
- 文件格式变了，在同一个 PR 里写一个内容迁移：按版本逐个执行，把存储桶里旧格式的文件改写成新格式，执行过的记下来，由内容导入在检查之前执行。
- 测试用的内容是测试自己的固定文件，放在测试的目录里，测试开始时传进临时的存储。

## 理由

- 内容和代码分开发布，加题、改题不用开 PR、不用发版，也不会因为内容改动触发代码的检查和风险评级。
- 流程只用形参、占位、排法、幕和顺序这几样通用的东西写，引擎就不会长出某个流程才有的概念；新的教法只加流程文件。
- 题目只有流程要的参数，换流程时检查能指出哪些参数对不上。
- 排法按区域写，主角和配角的大小由流程整体决定，不随组件的内容变；按屏幕条件选具体排法，手机、平板、电脑各有合适的样子。
- 颜色放进主题，同一套组件可以有几种配色，组件代码里不写颜色。

## 代价

- 内容没有 git 那样的历史和评审：改错了要从工作文件夹或别的备份恢复，发布前只靠检查和在测试环境里看。
- 开发机要有存储桶的写入凭据。
- 引擎的通用词汇要设计得够用：一个流程想表达的东西词汇里没有时，要先加通用词汇（改引擎、改格式、改检查），不能在流程里写脚本。
- 现有的流程和题目文件要按新格式重写。

## 何时重新考虑

- 内容多了、几个人一起编辑，需要历史、评审和合并：改成单独的内容仓库，或者给编辑做网页后台。
- 存储桶换成支持版本记录的服务，可以用版本记录恢复。
- 出现用通用词汇写不出来、只能用脚本表达的教法。

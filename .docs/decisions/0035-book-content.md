# 0035 书本数据和封面导入

## 背景

#9 的书库要一批书本：书名、简介、封面、学科、年级，还有下架和替代的书。内容只由平台团队制作，暂时没有管理后台。测试环境、开发机和测试里要有同样的书。

## 比较过的方案

- 书本信息放在哪里：只在数据库里，用迁移脚本修改；仓库里的 JSON 文件，由导入命令同步进数据库；连上各环境的数据库手工修改。
- 年级和学科：和书本一样在数据库里；仓库里的 JSON 文件。
- 示例书：写进迁移脚本；只给测试环境和开发机的种子数据。
- 封面图：放在仓库里，固定文件名，限定规格，不缩图；放任意原图，导入时用 sharp 缩图；不进仓库，由人传到各环境的存储。
- 封面导入命令：后端里用 NestJS 应用上下文启动的命令；`tools/` 下的独立脚本。

## 决定

- 年级、学科和书本只在 PostgreSQL 的表里，数据库是唯一的来源。书本表有编号、书名、简介、年级、学科、状态（`active`、`inactive`）和替代的书。
- 加书、改书、下架、删书，以及改年级和学科，都写成新的 SQL 迁移脚本，走 PR，由 `drizzle-kit migrate` 在每个环境执行。有家庭获取过的书，外键不让删。
- 30 本示例书写在迁移脚本里；建生产环境时再写一个脚本删掉它们。
- 封面图放在仓库的 `content/books/<书本编号>/cover.webp` 或 `cover.png`，WebP 或 PNG，不超过 300 KB，宽高比 3:4；导入时检查，不缩图。
- 封面导入是后端里的命令，入口 `apps/api/src/rebuild.ts`，任务命令是 `rebuild`，在迁移之后执行：按书本表找每本书的封面，校验全部通过才上传，再把封面的散列写进书本表。可以重复运行。

## 理由

- 数据库是唯一的来源，状态、替代的书这类会变的信息不会有两份。
- 迁移脚本走 PR，有评审和历史，每个环境按同样的顺序执行，开发机和测试里也有同样的书。
- 外键保证有家庭获取过的书删不掉。
- 不缩图就不用带原生二进制文件的图片库，封面由平台团队按规格做好。
- 封面导入和接口共用表定义、对象存储接入和配置校验，也受分层规则检查。

## 代价

- 改书本要写 SQL，而迁移脚本是高风险路径，每次都要人批准，合并后等 CD 发布才生效。
- 示例书会跟着迁移脚本进入以后的生产环境，建生产环境时要记得写脚本删掉。
- 封面不合规格，或者有书没有封面时，导入会停下。

## 何时重新考虑

- 书本多到写 SQL 吃力，或者要让编辑在网页上改内容。
- 建生产环境时。
- 教学和练习的内容格式确定时。

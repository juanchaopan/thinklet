# 0040 审计记录

## 背景

#14 之前，几张表在业务数据旁边记着「是谁做的」：`join_requests.closed_by`（谁同意或拒绝了申请）、`children.consent_parent_id`（谁勾选了监护人同意，连同 `consent_version` 和 `consented_at`）、`family_books.acquired_by`、`book_assignments.assigned_by`、`child_login_links.created_by`。这些列引用家长，删除家长账号时（决策 0038）就要处理它们。用户希望业务表只记最终状态，谁做了什么统一记在一张不删的审计表里。《个人信息保护法》要求注销后删除个人信息。

## 比较过的方案

- 「是谁做的」放在哪里：留在各张业务表里；统一放进一张审计表。
- 审计表里的「谁」：只存编号和标识；另存当时的名字和邮箱。
- 记哪些动作：每一个改数据的动作；只记代替那几列的动作再加删除；连登录和退出也记。

## 决定

- 新的后端模块 `audit` 负责写审计表 `audit_events`，其他模块在自己的事务里调用它导出的 service，审计和业务数据一起提交或一起回滚。
- 每一个改数据的动作写一行：时间、做事的人（种类是家长或孩子，以及编号；家长另存 Authing 的 issuer 和标识）、动作、对象（种类和编号）、家庭编号，以及动作本身的少量细节（比如监护人同意文字的版本）。登录、退出和只读的动作不记。
- 只存编号和标识，不存名字、邮箱、孩子的昵称和账号这类个人信息。
- 审计表只增不改不删：不引用别的表，删除家长、家庭和孩子时也不删。
- 业务表只记最终状态：上面那几列从表里去掉，已有的值由迁移脚本写进审计表。孩子的监护人同意记成审计表里的一条「添加孩子并同意」。
- 动作的名字和细节字段由设计定。

## 理由

- 业务表不再引用做事的家长，删除家长时不用一张张表去清空或改写，表的意思也更单纯。
- 一张表记下所有改动，查「谁在什么时候做了什么」只看一处；和业务数据在一个事务里写，不会有业务改了却没留记录的情况。
- 只存编号和标识：家长删掉后，他在 Authing 上的账号也没了，审计里的一串编号对不上任何人，和删除个人信息的要求不冲突；存名字和邮箱就会让删掉的人的个人信息永远留着。
- 每个改数据的动作都记才完整；登录次数多，记了表长得快，而且登录不改数据。

## 代价

- 每个改数据的接口多写一行，要记得调用审计的 service，漏了也不会报错，要靠测试检查。
- 表只增不删，会一直变大；几百个家庭的规模下一年也只有几万行。
- 审计里只有编号，人看的时候要对照还在的数据；删掉的人只剩编号。
- 页面上不再能显示「谁获取的、谁分派的」，要显示就得查审计表。

## 何时重新考虑

- 审计表大到影响备份或查询。
- 要给家长看操作记录。
- 法律意见认为审计里的编号或标识也要删除。
